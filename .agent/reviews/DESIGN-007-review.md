**Verdict: request changes. Two P2 findings.** The twelve item destinations, explicit quantity commits, bounds, fire states, and stated arithmetic meet their named criteria. Shared reconstruction of an existing order makes the zero-comp and overflow paths untruthful after Add.

## Findings, most severe first

### 1. P2 — Adding from `zero` silently removes its 100% comp and creates a payable balance

**Locations:** `docs/design/visual-directions/frost-order-flow.js:46,49–57,191–205`; `docs/design/visual-directions/frost/pos/order.html:334–340`.

In headless Chrome I opened `?state=zero`, which showed subtotal **165.000**, Comp 100% **−165.000**, and total **0**. I tapped Soda and pressed Add to order. The reconstructed model inferred the discount only from whether the visible totals contained “Staff meal” (`:199`); `zero` has “Comp 100%”, so it became undiscounted. The panel then showed subtotal **195.000**, no discount, service **9.750**, total **204.750**, and included tax **17.727**. With the existing comp retained, subtotal 195.000 should produce discount 195.000 and zero service, tax, and total. The shared Add control is correct in ordinary states and wrong in this one.

**Authority:** PRD FR-F1/F4/F5 and B-8 require the applied discount's snapshot to stay with the order; PRD FR-M4 and §4 define the money sequence. SCREEN-INVENTORY POS-03 names zero-total as a 100% discount state and requires order totals to derive from its held discount. DESIGN-007 requires every figure to remain coherent after an add.

**Recommended correction:** carry the existing discount kind and value explicitly into the composed order model. Keep Comp 100% through Add and recompute the zero result; test Add from every pre-existing discount state, including `zero`.

### 2. P2 — Adding from `overflow` erases its voided line from visible order history

**Locations:** `docs/design/visual-directions/frost-order-flow.js:61–69,191–205`; `docs/design/visual-directions/frost/pos/order.html:252–284`.

In `?state=overflow`, Round 1 contains a struck-through Caesar Salad with “Voided 19:51 · approved by M. Iqbal”. After tapping Soda and pressing Add to order, that row disappears. `readVisibleModel` skips `.line--void` (`:202`), and `renderOrder` replaces the full line list with only modeled rows (`:64`). The amount calculation after Add is otherwise correct: subtotal 1.185.000 + 30.000 = **1.215.000**, service **60.750**, total **1.275.750**, included tax **110.455**. The defect is that a valid add changes what the cashier can read about an earlier void. The same reconstruction also labels the old rounds “printed” although `overflow` did not show a delivery outcome.

**Authority:** SCREEN-INVENTORY POS-03 requires VOIDED lines to remain distinguishable and the order list to show round history; PRD FR-D3 permits adding after an earlier fire, while B-8 protects historical snapshots. DESIGN-007 criterion 8 requires unrelated state changes to be accounted for, and its handoff says prior fired rounds remain intact.

**Recommended correction:** preserve voided rows and known delivery values when composing the model and rerendering. An Add or later Fire should append new work without deleting or inventing historical display facts. Recheck the overflow path after both actions.
