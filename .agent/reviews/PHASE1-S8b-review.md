## Findings

### F1 — P2: Complete the own-password secret-scan paths and search its current password

**Location:** `apps/server/test/log-scan.test.ts:314`, `apps/server/test/log-scan.test.ts:340`, and `apps/server/test/log-scan.test.ts:452`.

The scan sends wrong and throttled current passwords only to `own-pin`. It never exercises those two states of `own-password`, although the two routes have separate handlers. Its successful `own-password` request also sends `own.password`, generated by `makePeople`, as `currentPassword`; that value is absent from both marker objects searched by the log assertions. The later `own-password` requests carry a searched current-password marker, but all fail schema validation before reaching verification. Consequently, the successful own-password verification path has no searched marker for that field.

This does not satisfy S8b AC 11 and copied C3 section 8, which require every new route and credential field to be scanned through success and the applicable refusal paths, including a wrong and a throttled current password for the own changes. Those checks are the required evidence for ADR-010 rule 2 and B-12. All explicitly declared `USERS_MARK` leaves are searched, so S8a's omitted-leaf defect has not returned; the gap is a credential outside that object and two missing route states.

**Concrete failing scenario:** a regression that logs the current password only after successful verification in the `own-password` handler can expose the generated password without matching the scan's searched strings. A regression confined to that handler's wrong-password or cooldown branch is never reached by this scan. I confirmed the first gap with an in-memory predicate probe: a synthetic nested log line containing the generated success credential matched zero of the 46 string markers from `USERS_MARK` and `MARK`. This was not an HTTP mutation run. The second scenario is inferred from the request list, not claimed as an executed mutation.

**Proposed fix:** give the own-password success case a distinct current-password marker included in the derived scan list, and exercise wrong and throttled attempts on both own routes, with searched markers in every credential field and exact refusal-envelope assertions. Also complete the extra-key validation case for `set-password`, which currently has only a malformed-value case. Prove the additions with temporary route-specific leaks, including one after successful own-password verification and one on its wrong/throttled path, then remove the mutations. Keep the PIN lookup searches and the existing username-view exception.

## Cleared

The following conclusions are based on source and test inspection unless a run is explicitly identified above.

**Credential and session behavior.** Both other-user commands lower-case the subject id and reject `OWN_ACCOUNT` before hashing or opening the transaction. Their active/classification/credential-row preconditions match ruling 8. Both own routes validate before verifying the guard's actor account; they then pass the verified credential version into the domain. The shared `changeOwn` tail checks that version under the actor lock, increments once, requires exactly one re-stamped row, and throws a rollback refusal otherwise. The SQL binds the session to the actor, back-office audience, unreleased state and old version. Same-value credentials still increment and audit. The shared helper was specifically checked across password, PIN, duplicate PIN, stale verification and released-session states; I found no hidden state-dependent production error.

**Lock order and hashing.** New-secret Argon2id hashing completes before the change transaction. `lockUsers` takes StaffUser rows in id order with `FOR NO KEY UPDATE`; its session read takes no row lock. Password changes then lock BackOfficeCredential, and own changes finally update ActorSession. Updating the already locked StaffUser version after the credential write does not acquire a previously unheld StaffUser row. The verifier's credential lock commits before the change begins. Password verification itself intentionally holds that lock across Argon2id verification under ADR-009 section 4; it does not hold it across hashing the new secret. Both password writes touch `password_hash` only, leaving throttle reset to successful verification.

**Race-test windows.** The reasoning for domain-level AC 5 and AC 6 is sound for this fixture: holding ActorSession before starting an HTTP request would block the guard's interactive UPDATE before the handler, rather than block the re-stamp. The domain tests instead leave the session's old committed row readable, wait for the command's lock wait, and test visibility or release at the re-stamp. AC 15's StaffUser holder allows the guard's session UPDATE and the verifier's `FOR UPDATE OF c` to complete before blocking `lockUsers`; bumping the version then produces the intended domain refusal. Its exact body excludes `csrfToken`, and it separately checks the absent cookie header. This test simulates the version movement; AC 16 separately uses the real other-manager password-reset route. These windows were inspected, not independently executed here.

**Current-password answers.** `verifiedUser` preserves C3 section 4 and ADR-011 rules 7 and 9: a failed match is 401 `INVALID_CREDENTIALS`, details appear only when that failure starts cooldown, and an existing cooldown is 429 `THROTTLED`. Schema refusals precede verification and count nothing. The unchanged verifier commits strikes before writing anonymous security telemetry. The own-change handlers neither renew nor issue sessions, cookies or anti-CSRF tokens. The no-cookie promise applies to handler outcomes after a successful guard; a session rejected by the ordinary guard still has the cookie-clearing behavior required by ADR-011.

**Audit and confidentiality.** Each success uses a fixed action, identified actor and subject, with the audit write on the same transaction client. The four audit-failure cases assert rollback of credentials, version and session behavior. The audit scan includes the added new-credential markers and their PIN lookups. Its first own-password current value is also generated rather than a searched marker; the separate exact audit-row assertion still checks the writable free-text `reason` as null. No production statement passes credential data to audit or logging. PIN uniqueness is delegated to the named partial index, and database errors are replaced rather than exposed. The re-stamp source scan covers both source and scripts, as ruling 3 requires.

**Test order and red-proof quality.** The builder explicitly departed from test-first development; the handoff is not evidence that tests preceded implementation. Several reported reds fail earlier than their narrative endpoint, but on the named invariant: missing increments fail version assertions, and schema-before-verification fails the response assertion before the count assertion. AC 13 correctly separates the former-manager role check from the missing-credential-row check; dropping the latter alone cannot make a former cashier pass the former. The timeout failures caused by skipping re-stamping are not evidence for AC 5 or AC 6, but the separately recorded post-commit re-stamp and ignored-row-count mutations target those criteria directly. The audit mutation's exact-row failure proves that an unexpected reason is rejected; it does not independently prove the marker-scan assertion. I have not promoted any of those recorded mutations into reviewer-observed results.

**Scope and client declarations.** The incremental production changes stay within S8b's owned paths. There is no migration, new error code, POS change or screen change. The unchanged access and route-table tests were inspected as coverage, not claimed as rerun. The contract and back-office configuration declarations passed the focused run above. No screen behavior is inferred from domain tests or fixture navigation; BO-06 and its real browser paths remain S8c's work.
