## 2. Findings, most severe first

### Finding 1 — The version a list edit carries is not defined, and the fixture moves it on every command answer. A rename or reorder can therefore silently rebase onto data the page has never read.

- **Location:** `docs/design/visual-directions/frost/back-office/menu.js:80` (`base:version` when an editor opens), `menu.js:141` (`if(changed)version++` on every applied command, state commands included), `menu.js:313` (the partial fixture). The rule as written is at `.agent/tasks/DESIGN-019-menu.md:291` ("carry the catalog version read when their editor opened") and at `docs/DESIGN.md:1797` ("carrying the catalog version read when the draft opened").
- **What is wrong:** BO-03 is a list of many records under one global catalog version (ADR-012 rule 9). Under C2 §3, a successful command replaces only its own record and does **not** reread the list. Under ADR-012 rule 15, the answer carries the version the command produced. That number covers every catalog write by anyone up to that moment, not just this page's write. The fixture keeps one `version` variable that serves as the server's version, the version of the page's last read, and the version of the last command answer, all at once. The design never says which of these a newly opened rename or reorder carries. "Read when the editor opened" can be taken to mean "the latest version this page knows", and ADR-012 rule 15 nudges a builder that way ("so that a tab continuing to edit carries the right number without a re-read"). On a single-record form that reading is safe (BO-08). On a list it is the silent rebase that D's stale-draft rule forbids: "A reread alone never moves it, because a draft silently rebased onto a reread would overwrite whatever that reread contains" (`docs/DESIGN.md:1656-1660`, from ADR-012 rules 3 and 13). This is the shape the role prompt warns about: one value shared across states, wrong in only one of them.
- **Authority:** ADR-012 rule 13 (an edit carries "the catalog version its form was read at" and is refused when stale); `D` *The stale-draft refusal — behaviour* (DESIGN-018); C2 §3 (no list reread after success).
- **Failing scenario:** Tab A reads the menu at version 12 and shows the category "Mains". In tab B, a second manager renames Mains to "Main dishes" (version 13). In tab A, the manager marks Steak 86, and the answer carries version 14. If S4c follows the fixture, tab A now stands at 14 while its Mains row still says "Mains". The manager opens Rename on Mains (draft "Mains", base 14), types "Main plates" and saves. The server's version is 14, so the edit is accepted, and B's rename is overwritten by a manager who never saw it. The two reorders have the same exposure: the reorder sends a full order built from rows that may be out of date, yet carries a current version, so another tab's reorder is reversed without a refusal.
- **Proposed fix:** Write the rule into the Handoff's rules table and into `D`'s DESIGN-019 *Catalog changed during a list edit* paragraph, and make the fixture keep a separate `listVersion`. Proposed wording: "BO-03 keeps the version its list stands at. A full read sets it. A command answer advances it to the answered version only when that version is exactly the standing version plus one, or equal to it for an unchanged answer. Otherwise the list keeps its standing version, so the next edit opened from it is refused `CATALOG_CHANGED` and rereads. An editor carries the list's standing version at the moment it opens." Add a `design019.cjs` assertion: after a state command whose answer skips a version, the next rename is refused stale.

### Finding 2 — The 86 result says the item is "disabled in place" at the POS even when the POS does not show it at all

- **Location:** `menu.js:145`, which is the copy row at `.agent/tasks/DESIGN-019-menu.md:411` ("`{name} is now marked 86. At the POS it is disabled in place, not removed.`").
- **What is wrong:** The 86 result is one sentence shared by every item. But 86 and Make available stay on archived items and on items in archived categories (Handoff line 290; C1 §3, "An archived item may be marked either way; it is not offered"). For those items the second sentence is false: under C1 §2.2 *What the POS may offer*, they are not offered at the POS, so they are hidden there, not disabled in place. The available-again result handles this case correctly with an added qualifier ("It stays hidden from the POS while it or its category is archived.", `menu.js:146`, Handoff line 413). The 86 result has no equivalent. This is the same shared-value shape as finding 1, here in copy.
- **Authority:** C1 §2.2 *What the POS may offer*; C1 §3; AC-12 ("disables it in place … never removed") describes an item the POS offers. ADR-011 rule 24 makes these words S5's verbatim copy.
- **Failing scenario:** In `default`, press *86* on Apple Pie (category Seasonal is archived) or on Winter Stew (archived item). The page says "Apple Pie is now marked 86. At the POS it is disabled in place, not removed." No POS shows Apple Pie at all.
- **Proposed fix:** For an item that is archived or whose category is archived, replace the second sentence with the existing qualifier pattern. Proposed wording: "`{name} is now marked 86.` It stays hidden from the POS while it or its category is archived." Add the row to the copy table, and add a check that 86 on `pie` and `stew` does not contain "disabled in place".

### Finding 3 — *Reorder categories* stays enabled while the menu is loading or failed to load, and opens a reorder of rows the page says it could not read

- **Location:** `menu.js:42` (`$('#reorder-categories').disabled=categories.filter(x=>x.active).length<2||!!pending;`) and the opener at `menu.js:248`.
- **What is wrong:** The control's enabled state ignores `read`. In `loading` and `error`, the fixture still holds four categories, three of them active, so the button is enabled. Pressing it opens the non-modal editor, which sits outside the hidden `#menu-list`, with "1. Mains, 2. Sides, 3. Drinks" and a base version, while the page says "Loading menu…" or "Menu could not be loaded". *New category* is correctly disabled during loading (`menu.js:43`). A reorder "sets the full order of one scope" (C1 §2.2 *Display order*; `reorderCategories` is refused `VALIDATION_FAILED` for "a list that is not exactly the active categories", C1 §2.3). So it needs a complete read, which the page does not have in `loading`, in `error`, or in `partial`, where by D's F4 wording the list "may be out of date". D-018's F4 rule keeps only *New* live in that state.
- **Authority:** C1 §2.2 and §2.3; `D` *A success while the list read stands failed* (DESIGN-018), which keeps New live and says nothing of reorder; `D` *Validation and refusal* ("Read failure offers Try again to repeat only the read").
- **Failing scenario:** Open `menu.html?state=error`, then press *Reorder categories*. The reorder panel opens over a page that says "Menu could not be loaded", listing three categories and allowing *Save order*. Built that way in S4c, the command would carry no version that was ever read, or the version of a failed read.
- **Proposed fix:** Disable *Reorder categories*, and each category's *Reorder items*, unless `read==='ready'`. State it in the Handoff's *Reorder* rule and in `D`'s reorder paragraph ("A reorder needs a complete read: its openers are disabled while the list is loading, failed or partial"). Extend the check to assert both openers are disabled in `loading`, `error` and `partial`.

### Finding 4 — The inventory says every create is immune to `CATALOG_CHANGED`. C1 refuses an item create into an archived category with exactly that code.

- **Location:** `docs/design/SCREEN-INVENTORY.md:703-704`: "Creates and state commands never carry the catalog version and cannot be refused for a stale catalog."
- **What is wrong:** The task's ruling, the Handoff (line 292) and `D` (`docs/DESIGN.md:1819-1821`) all scope this correctly to the **category** create. The inventory sentence covers all creates, and the BO-03 entry is where *New item* starts. C1 §2.3's command table says `createItem` into an archived category is refused `CATALOG_CHANGED` ("the only way to name one is a form read before it was archived"), and C1 case C-16 tests it. ADR-012 rule 13 says a create's preconditions are checked against current state. It does not say a create is never refused.
- **Authority:** C1 §2.3 (`createItem` row) and §2.4 C-16; ADR-012 rule 13 (*A create does not carry it … Its preconditions … are checked against current state*).
- **Failing scenario:** A DESIGN-020 designer or an S4c/BO-04 builder reads `I` BO-03, which is the authority for the screen that launches *New item*, and concludes that BO-04's create needs no `CATALOG_CHANGED` handling. A manager opens *New item in Seasonal* just before another tab archives Seasonal. The create is refused `CATALOG_CHANGED`, and there is no drawn state for it.
- **Proposed fix:** Replace the sentence with: "A category create and the state commands never carry the catalog version and cannot be refused for a stale catalog. An item create (BO-04) carries none either, but is refused `CATALOG_CHANGED` when its category has been archived (C1 §2.3)." Add the same line to the Handoff's *For DESIGN-020* paragraph.

### Finding 5 — The lead's item 1: BO-03 draws the future rail, where the Phase 1 precedent draws the Phase 1 rail

- **Location:** `menu.html:8` (an empty `<nav class="bonav">`, which `office.js:14-25` fills with the full future rail); `docs/DESIGN.md:1841-1842` and Handoff line 300 ("The shared review rail retains future destinations").
- **What is wrong:** C2 §7 says "The rail lists only destinations that exist" (DESIGN-016 Part B 4). DESIGN-017 drew a Phase 1 rail on `tables.html`. DESIGN-018 extended it when it drew the next Phase 1 screen: "The Phase 1 rail lists Tables and Settings; `tables.html`'s drawing now shows both" (`docs/DESIGN.md:1765-1766`). Both `tables.html:9` and `settings.html:9` author that rail in HTML. BO-03 is the third Phase 1 screen (S4c), but its drawing shows Today, End of day, Reports, Audit, Staff, Discount presets and Printing, five of which do not exist in Phase 1. Meanwhile Tables and Settings do not list Menu. The walk is therefore asymmetric: from Menu the rail reaches Tables, but from Tables no rail entry leads back to Menu. The Handoff's sentence that "S4c must use the production built-destination manifest" pushes onto the builder the decision that DESIGN-017 and DESIGN-018 drew for theirs. The `D` addition's sentence contradicts the DESIGN-018 rule without saying it changes it, and the task says "Change no existing rule".
- **Authority:** C2 §7 *The manifest and the rail*; `D` *BO-08 copy and layout* (DESIGN-018), and *BO-05 choices and copy* ("other gallery artifacts retain their future rail" covers screens that are not Phase 1, which BO-03 is not).
- **Failing scenario:** A reviewer, or S4c, takes `menu.html?state=default` as the drawing of BO-03's Phase 1 frame and sees seven destinations that Phase 1 cannot route to.
- **Proposed fix:** My recommendation is the Phase 1 rail. Author it in `menu.html` as Configuration → Menu, Tables, Settings (the future rail's order), with `data-nav="menu"` current. Add *Menu* to the authored rails of `tables.html` and `settings.html`, as DESIGN-018 added Settings. Replace the `D` sentence with "The Phase 1 rail lists Menu, Tables and Settings; `tables.html` and `settings.html` now show all three." I read the earlier checks for what this touches. `design017.cjs:111` and `design018.cjs:197` assert only that the menu page's Tables and Settings entries resolve to Frost, so they still pass. `design014.cjs`'s authored prototype-link count for `menu.html` stays 0, because the Phase 1 entries are local. The six earlier checks would need a rerun, since `tables.html` and `settings.html` change.

### Finding 6 — The lead's item 2: the *86* control's accessible name is sound, but *Make available* and *Move up* / *Move down* fail label-in-name

- **Location:** `menu.js:50` (availability button) and `menu.js:75` (move buttons); copy table rows at `.agent/tasks/DESIGN-019-menu.md:369` and `:393`.
- **What I found:** The *86* button's visible text is "86" and its accessible name is "Mark {name} 86", for example "Mark Steak 86". The visible label is contained in the name, so it meets WCAG 2.2 SC 2.5.3 (*Label in Name*), and a speech-input user saying "click 86" reaches it. The name also says what the command does, which bare "86" does not. That one is cleared. The available-again button's visible text is "Make available", but its name is "Make {name} available" ("Make Soda available"). The visible string "Make available" does not occur in that name, because the item name splits it. The move buttons behave the same way: visible "Move up", name "Move Steak up". SC 2.5.3 requires the name to contain the visible label's text, and the W3C *Understanding* note recommends that it start with it. A speech user saying "click Make available" or "click Move up" may get no match. Every other row and header control in the table (Rename, Archive, Restore, Reorder items, New item, Edit) starts its name with its visible label, so the two failures are the exceptions.
- **Authority:** WCAG 2.2 SC 2.5.3 (Level A); `D`'s accessible-name practice in the earlier configuration screens, which name controls as "{visible label} {subject}".
- **Failing scenario:** With a speech-input tool, a manager says "click Make available" on Soda's row. The accessible name "Make Soda available" does not contain that phrase, so the command is not matched.
- **Proposed fix:** Keep the visible text and start each name with it: "Make available: {name}", or "Make available {name}", and "Move up: {name}" / "Move down: {name}". Update the copy table, which S4c and S5's tests drive by accessible name. Optionally, align the 86 name the same way ("86: {name}" or keep "Mark {name} 86"; both pass). Leave that to the lead, since "Mark {name} 86" reads better aloud.

### Finding 7 — An 86 pressed while a category draft is dirty waits behind a "Discard unsaved changes? … before leaving" decision. That conflicts with the task's urgency ruling, and the Handoff does not record the choice.

- **Location:** `menu.js:236` (the availability click goes through `leave(...)`); `menu.js:95` (the decision's body, "Stay to keep editing, or discard them before leaving.").
- **What is wrong:** The task's ruling says "An 86 is urgent and must act at once from the row." With a dirty rename or reorder open, pressing *86* opens the modal departure decision with focus on *Stay*. The 86 only runs after *Discard*, and the copy speaks of "leaving", which the manager is not doing. This follows `D`'s DESIGN-018 rule *Two forms on one screen* ("Every opener on the screen (each Change, New, Edit, Deactivate and Reactivate) goes through the departure decision …"), so the designer did not invent it. But that rule was written for screens where nothing was urgent, and the Handoff and `D`'s DESIGN-019 additions neither mention the conflict nor give a reason. There is a defensible reason to keep the gate: an 86 advances the one catalog version (ADR-012 rule 10), so the manager's own 86 would make their open rename or reorder stale and lead straight into the `CATALOG_CHANGED` comparison.
- **Authority:** the task's ruling *ADR-012 rule 13, as BO-03 meets it* ("An 86 is urgent and must act at once from the row"); `D` *Two forms on one screen*; ADR-011 rule 24 (the decision's words become product copy).
- **Failing scenario:** The manager is midway through reordering Mains when the kitchen calls Steak out. They press *86* on Steak. A dialog asks whether to discard unsaved changes "before leaving". Pressing Enter keeps the draft and does **not** 86 Steak, because focus starts on *Stay*.
- **Proposed fix:** This is the lead's call, so I offer two options. (a) Keep the gate, and record in the Handoff and in `D`'s *State commands on grouped lists* that a state command with a dirty editor open goes through the departure decision, and why (the command would make the draft stale). (b) Let the state commands act at once and keep the draft, accepting that the draft will meet the `CATALOG_CHANGED` comparison on Save. Either way, the decision's body for this case should not say "leaving". Under (a), proposed wording: "Your edits have not been saved. Stay to keep editing, or discard them to continue."

## 4. Cleared

- **ADR-012 rule 13's split:** rename and both reorders carry a version. Category create, 86, available again, and archive and restore of items and categories carry none (`menu.js:123`, `:127`). The check asserts this for every command in every state. No state suggests a state command or a create can be refused for a stale catalog, and the fixture's response selector coerces `stale` to `saved` for them (`menu.js:157`).
- **Rule 10:** every committed write, including 86, archive and restore, advances the version once, and a no-op does not (`menu.js:135-141`). The `I` text states this.
- **The stale refusal on rename and reorder** follows `D`'s DESIGN-018 rule. Nothing is written; the draft or order is kept; there is one reread; the current name or full order is shown beside the draft; Save is disabled with a visible reason until *Keep my changes* or *Use current menu*; focus moves as tabled; nothing is resent. *Unknown with a newer version* and *stale with a failed reread* are both drawn. Save is offered on an unchanged draft ("Nothing changed. Menu version {n} is still current.").
- **State commands open no form** and report results on the page (pending, done, unknown, failure, session refusal), with no resend control. *Category archive without confirmation* follows the lead's ruling, and both the header note and the result say what it hides and that items are unchanged (C1 §2.2).
- **Archived categories** keep their items visible with their own flags, under "Hidden from the POS · category archived". *New item* and *Reorder items* are absent until restore. Retention holds (FR-C8, B-8): nothing on BO-03 deletes anything.
- **Names:** trimmed; 1–32 UTF-16 units; Cc refused; checked in the order empty, length, controls; no maxlength. Unique among active categories, case-insensitively, on create, rename of an active category and restore. Renaming an archived category is allowed and does not restore it. Item restore into a held name is a page result whose way out is the item's own Edit (C2 §4). The overflow fixture's longest category is exactly 32.
- **Reorder without dragging:** Move up and Move down, edge buttons disabled, keyboard-operable, focus kept on the moved record, full-scope *Save order*, archived records outside the scope, and openers disabled below two active records. I found no drag-only path.
- **Phase 4 lease refusal:** marked in the artifact (`#phase-note`) and the gallery label. It names Quick-sale order ORD-1048 (opened 20:14) and uses DESIGN-011's wording, matching FR-G13, AC-29 and ruling C-4 (quick-sale only).
- **Subject identity:** every Edit link carries its own row's `item`, `category` and `returnItem`, and the check compares every row. 86, archive and restore act on, and announce, the pressed row. Rename, Cancel and Discard return focus to the subject's opener. Fixture counts are derived from records.
- **Session gates:** M-6 over an inert, visible form; BO-01 closes the departure dialog and hides the frame; the same manager recovers the draft and any held decision without a resubmission; a different manager destroys it.
- **Money:** stored tax-inclusive base price, whole rupiah, `.` grouping, no symbol. There is no price input on BO-03.
- **Scope and boundaries:** no audit trace (Q11), stock, image, timing control, nested modifier group or POS operation. People are named (M. Iqbal, Ratna Ayu; B-13). The empty state is real (B-24). No change was made to `P/item-editor.html`, the product documents, ADR-012, C1 or C2. `menu.css` uses tokens only, with no new token and no success green.
- **Part C:** `office.js` already resolves Menu to Frost. The gallery's Paper list is kept separately (`paperStates`). `design014.cjs` changes only its expected authored count (34 → 0), and no assertion is weakened.
- **Open question:** C1 lists no `reorderItems` command. The question is raised with a proposed answer, and the lead has settled it for S4a's task file.
- **For DESIGN-020, not a finding here:** items in an archived category keep `is_active`, so under C1 §2.2's partial unique index their names stay held while the category is archived. An item create elsewhere with such a name would be refused `DUPLICATE`, and BO-04 should say why.
