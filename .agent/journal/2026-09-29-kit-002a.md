## Context7 reaches Codex by two routes

`codex mcp list` shows `context7` as a config server (`[mcp_servers.context7]`,
`npx mcp-remote`, enabled). Separately, the ChatGPT account has a **Context7
app** (connector `asdk_app_69ef18c674308191a2f952431f91ea61`), which Codex
exposes through its `codex_apps` server while the `apps` feature is on (it is,
by default). The librarian's proof run below called Context7 **through the
app**, not through the config server.

Four `codex exec` runs, same prompt ("call a Context7 resolve-library-id for
react, reply CALLED or UNAVAILABLE"), gpt-6-luna, read-only:

| Per-run flags | Result |
|---|---|
| none | called `context7/resolve-library-id` (config server) |
| `-c mcp_servers.context7.enabled=false` only | Codex tried `codex_apps/context7.resolve-library-id` (the app was still offered; the call failed) |
| that, plus `-c apps.asdk_app_69ef…enabled=false` | UNAVAILABLE, no MCP call |
| that, plus `--disable apps` instead | UNAVAILABLE, no MCP call |

So a non-librarian Codex run needs **both** the config-server flag and the
app flag. The narrower app flag is recorded in agents.yaml
(`launch.codex.mcp_off.context7`) rather than `--disable apps`, which would
also remove every other ChatGPT app.

The answer, verbatim:

> **Yes for all three.** Codex and OpenCode can disable particular discovered
> skills; Claude Code can hide individual skills through settings or restrict
> invocation. There isn't a documented per-run skills flag for Codex or Claude
> Code; both can use config/settings files, while OpenCode supports per-agent
> config.
>
> | CLI | Exact control | Effect |
> |---|---|---|
> | **Claude Code** | Per-skill `skillOverrides` in settings: `"skill-name": "off"`; pass a settings file for a run with `--settings <file>`. Alternatively, `disable-model-invocation: true` in `SKILL.md` frontmatter. | `"off"` hides the skill and blocks invocation. `disable-model-invocation` removes its description from context and prevents Claude from invoking it, but leaves it manually invokable by the user. Denying `Skill` in permissions blocks tool use; it is an invocation restriction, not the documented visibility control. **Not per agent.** ([skills docs](https://code.claude.com/docs/en/skills#override-skill-visibility-from-settings), [CLI reference](https://code.claude.com/docs/en/cli-reference)) |
> | **OpenAI Codex CLI** | `[[skills.config]]` with `path = "/…/SKILL.md"` and `enabled = false` in `~/.codex/config.toml`. | Disables that skill; the docs call this "disable a skill without deleting it." The setting is config-based, not documented as per-agent or a CLI flag. **Per run:** not documented. ([Codex skills docs](https://developers.openai.com/codex/skills#enable-or-disable-local-codex-skills), [config reference](https://developers.openai.com/codex/config-reference#skillsconfig)) |
> | **OpenCode** | V1: `permission.skill` patterns with `"deny"`; custom agent frontmatter `permission.skill`, or `agent.<name>.permission.skill`. Also `tools.skill: false` disables the tool. V2: `permissions` rules with `{ action: "skill", resource: "<id/pattern>", effect: "deny" }`, scoped under the agent's permissions for per-agent rules. | V1 docs say denied skills are hidden from agents and access is rejected; disabling the tool removes the available-skills section. V2 likewise says `deny` hides and rejects loading. **Per-agent supported.** ([OpenCode skills docs](https://opencode.ai/docs/skills), [V2 permissions](https://opencode.ai/v2/docs/permissions)) |
>
> **Context7 was used first** for all three CLIs. It returned the Codex disable
> configuration and OpenCode skill permissions. For Claude Code, it surfaced
> skill invocation controls but not the settings visibility override; I
> verified that detail in Anthropic's official docs.

Where the lead's checks below go further than this answer, the checks win:

`--settings` takes inline JSON, not only a file.

## Skills gating, checked per CLI

Each CLI's own list of loaded skills was read before and after a per-run
override.

- **Claude** (`skillOverrides` through `--settings '<json>'`, read from the
  init event's `skills`): `grill-me` off → 135 to 134, gone. A claude.ai-synced
  skill (`anthropic-skills:docx`, from `~/.claude/skills/synced/`) goes off by
  its full name or its bare name. Bundled skills (`batch`, `simplify`, …) go
  off too. **A plugin skill does not**: `superpowers:brainstorming`,
  `brainstorming` and `superpowers@claude-plugins-official:brainstorming` all
  left it listed. Plugin skills go only with the whole plugin
  (`enabledPlugins`).
- **Codex** (`-c 'skills.config=[{path="…/SKILL.md",enabled=false}]'`, read
  from `codex debug prompt-input`): `grilling` off → 159 to 158; a system skill
  (`imagegen`) and plugin skills go off the same way.
- **OpenCode** (`OPENCODE_CONFIG_CONTENT='{"permission":{"skill":{"*":"deny","herdr":"allow"}}}'`):
  `opencode debug agent build` shows the two rules; a real `opencode run`
  (openai/gpt-6-luna) asked to name the skills in its skill tool answered
  `herdr` only, against 74 skills without the override. `opencode debug skill`
  lists every installed skill whatever the permission, so it is the inventory,
  not the gate.

The generated gates, applied end to end:

- `skills-report.sh --gate designer codex` (17 438 characters of `-c`) →
  Codex lists `herdr`, `impeccable` and nothing else.
- `--gate builder claude` → init lists `herdr` plus the seven `caveman:*`
  skills. Caveman stays on by design: its plugin also carries the chat-mode
  hooks, and `caveman_off` governs it.
- `--gate architect claude`, with caveman off as for a caveman-off role →
  `grill-me herdr`.
- `--gate builder opencode` → the allowlist above.

## grill-me is not a skill a model can use

`~/.agents/skills/grill-me/SKILL.md` has `disable-model-invocation: true` and
its whole body is "Call the Skill tool with `grilling`". Codex does not list it
at all; Claude lists it but the model cannot invoke it. The working skill is
`grilling`. With the architect gated to `[herdr, grill-me]`, `grilling` is
hidden and the stress-test skill is unusable.
