## Things the session learned, in the order they cost time

**A permission prompt can stall a builder for hours without waking the lead.** On FE-031 the
builder asked to run a read-only `grep` at 11:53. The dispatcher printed `BLOCKED ON APPROVAL`
and kept waiting; nothing wakes the lead until the dispatcher exits, and the harness killed the
background task at its two-hour limit. From FE-032 on, the lead also ran a background watch
after every dispatch or resume: loop until `herdr agent get <id>` reports `working`, then
`herdr agent wait <id> --until blocked`, then read the pane. It caught the next `grep` prompt
within minutes. The wait returns the moment the agent is blocked, so it must be re-armed after
each prompt. Two kit changes would remove the need, both the owner's call and both listed in
STATE.md: `Bash(grep:*)` on the builder allowlist, and a dispatcher that pings the lead.

**The lead's list of tests expected to change was wrong twice in spirit and once in fact.** For
FE-032 the explorer was asked which tests pin the absence of a Refund control and returned the
two whose titles say so. Fourteen more assertions pinned it through a shared `DEFAULT.buttons`
constant. The builder stopped rather than edit them, which was right, and the lead ruled the
edits in; but it used one of the two fix cycles. For a task that adds a control to a screen
already built, grep the test file for the exact control list.

**The review found what a browser cannot reach.** FE-032's first review found that a refusal
from the book (`not-closed`, `unknown-order`) left the screen with no order to draw and so no
refusal notice. A correctly built sheet cannot produce those refusals, so the lead's walk had
no route to them. The reviewer got there with a stub book through an in-memory test transform.
The lead's walk and the reviewer's reading cover different ground; a `ui` task that also has an
operation behind it needs both.

**The local `development` was stale after every merge.** The owner merges on GitHub and pulls
somewhere other than the main checkout. The lead fast-forwarded it three times
(`git pull --ff-only origin development`). The dispatcher cuts worktrees from the local branch,
so a dispatch without this would have built on an old tree.

**Scripted browser walks have three traps.**
- Several `.click()` calls in one script run against stale React state: a typed reason lost a
  letter. One click per `javascript_tool` action, many actions per `browser_batch`, is reliable.
- Timers are throttled in a background tab, so a script with many awaited delays ran past the
  45-second limit and looked like a frozen page. It was not the app.
- Tool output that looks like a query string is blocked, and so is text containing `=` (the
  sheet's *Cash: 100.000 − 26.750 = 73.250.*). Replace `=` before returning text, and report a
  URL's parameters as words, not as the string.

The dev server for a walk is `npm run dev -w apps/pos -- --host 127.0.0.1 --port 5183
--strictPort` in the task worktree; stop it afterwards (`lsof -ti tcp:5183 | xargs kill`).

**Codex reviewers cannot open a browser.** All four reviews this session reported
`listen EPERM` or an approval policy of `never`. For every `ui` task the lead's Chrome walk was
the only visual evidence, and each review said so plainly.
