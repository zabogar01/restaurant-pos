# 2026-09-29 — KIT-003 evidence

## The playbook's hook layout had a hole

The playbook sets `git config core.hooksPath .githooks`. Git resolves that
path inside the checked-out tree, so the hooks exist only on branches that
contain `.githooks/`. The first test matrix showed it: a commit on
`development` (which does not have the folder yet) ran no hook at all and
passed. The same layout also let an agent disable its own guard by editing
`.githooks/pre-commit` in its branch. And because the hook read `agents.yaml`
from the working tree, a builder could widen its own `owns:` and have that
same commit pass.

**Fix:** `.agent/bin/install-hooks.sh` copies the hooks and a snapshot of
`agents.yaml` into the shared `.git/hooks`, which is common to every worktree
and is not part of any branch. The hook reads the snapshot and the task file's
committed frontmatter. `core.hooksPath` is left unset, and the installer
refuses to run if it is set.

## In the real repository

Hooks installed into `restaurant-pos/.git/hooks`; `--check` reports current.
On `agent/agent-kit`, `docs/BOUNDARIES.md` was staged and committed twice:

```
pre-commit: docs/BOUNDARIES.md is a contract file: only the owner changes it (ALLOW_CONTRACT=1). Propose exact wording instead.
commit exit=1
pre-commit: docs/BOUNDARIES.md is a contract file: only the owner changes it (ALLOW_CONTRACT=1). Propose exact wording instead.
commit (AGENT_ROLE=builder) exit=1
```

HEAD stayed at `a1d67d0`, and the file was restored.

## GitHub

`main` was already on `origin` at `881a36d`, pushed by the owner. Protection
was applied with `gh api -X PUT …/branches/<b>/protection` and read back:

```
main: pr_required=true approvals=0 enforce_admins=true force_push=false deletions=false
development: pr_required=true approvals=0 enforce_admins=true force_push=false deletions=false
```

No direct push was attempted against either live branch. If protection had
been wrong, that push would have changed `development`, so the read-back is
the evidence.
